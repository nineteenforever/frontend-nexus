# codegraph 与 GitNexus 测评任务拆分

## 0. 本轮目标

本轮先做小规模实操测评，不追求一次覆盖所有仓库。

目标：

1. 在内网安装并跑通 `codegraph` 和 `GitNexus`。
2. 选择 2 个离线代码仓库：
   - 1 个 Java 项目
   - 1 个 Vue 项目
3. 使用内部 agent 按 `codegraph-gitnexus实操测评方案.md` 执行：
   - `Baseline`
   - `codegraph`
   - `GitNexus`
4. 每个仓库输出一份单仓测评报告。
5. 最后输出一份 Java/Vue 两仓综合对比结论。

本轮重点回答：

- `codegraph` 和 `GitNexus` 能不能在内网顺利安装、索引、被 agent 调用。
- 相比 Baseline，两个工具是否提升准确率。
- 是否减少文件读取、搜索次数、响应时间、token 或代理 token。
- Java 项目和 Vue 项目上收益是否不同。

## 1. 推荐人员分工

建议最少 4 个角色。一个人可以兼多个角色，但职责要分清。

| 角色 | 人数 | 职责 |
| --- | ---: | --- |
| 测评负责人 | 1 | 控制范围、确认仓库、验收报告、做最终判断 |
| 工具安装负责人 | 1 | 在内网安装 codegraph/GitNexus，配置 agent 调用方式 |
| 测评执行人 | 1-2 | 用 agent 跑 Java/Vue 两个仓库的三臂测评 |
| 结果复核人 | 1 | 检查评分、公平性、证据是否可靠 |

如果人手有限，推荐组合：

- A：测评负责人 + 结果复核
- B：工具安装
- C：测评执行

## 2. 总体任务拆分

```text
阶段 1：准备测评环境
阶段 2：安装 codegraph 和 GitNexus
阶段 3：选择 Java/Vue 仓库并冻结版本
```

## 3. 阶段 1：准备测评环境

负责人：工具安装负责人

输入：

- 内网机器或容器。
- 内部 agent 可用环境。
- Java 项目源码。
- Vue 项目源码。
- `codegraph-gitnexus实操测评方案.md`
- `实验方案工具安装.md`

任务：

1. 确认基础环境：

```bash
git --version
node --version
npm --version
java -version
mvn --version || gradle --version
python --version
```

2. 确认内部 agent 能执行：

- shell 命令
- 文件读取
- 文本搜索
- MCP 或工具调用
- 工具调用日志记录

3. 创建统一输出目录：

```text
benchmark-cg-gn/
  config/
  repos/
  repo-results/
  aggregate/
```

产物：

```text
benchmark-cg-gn/config/environment.md
```

内容包括：

- 机器信息
- agent 类型和模型
- Java/Node/Python 版本
- 是否可记录 token
- 是否可记录工具调用日志

验收标准：

- 环境检查命令有记录。
- agent 能正常读取仓库并执行 shell。

## 4. 阶段 2：安装 codegraph 和 GitNexus

负责人：工具安装负责人

参考文档：

```text
实验方案工具安装.md
```

### 4.1 安装 codegraph

任务：

1. 从内网制品库或离线包安装 `codegraph`。
2. 配置内部 agent 可调用 `codegraph` MCP。
3. 在一个小型 smoke repo 上执行：

```bash
codegraph --version
codegraph init -i
codegraph serve --mcp
```

4. 让 agent 调用一次：

```text
请使用 codegraph 查询当前仓库的主要入口、调用关系和影响范围。
```

产物：

```text
benchmark-cg-gn/config/codegraph-install.md
```

记录：

- 安装方式
- 版本
- MCP 配置
- smoke test 是否通过
- 失败问题和解决方式

### 4.2 安装 GitNexus

任务：

1. 从内网 npm registry 或离线包安装 `GitNexus`。
2. 配置内部 agent 可调用 `GitNexus` MCP/CLI。
3. 在 smoke repo 上执行：

```bash
gitnexus --version
gitnexus analyze --skip-embeddings
gitnexus mcp
```

4. 让 agent 调用一次：

```text
请使用 GitNexus 查询当前仓库的主要模块、工作流、风险或调用关系。
```

产物：

```text
benchmark-cg-gn/config/gitnexus-install.md
```

记录：

- 安装方式
- 版本
- MCP 配置
- smoke test 是否通过
- 是否开启 `--skip-embeddings`
- 失败问题和解决方式

验收标准：

- `codegraph` 能完成索引并被 agent 调用。
- `GitNexus` 能完成 analyze 并被 agent 调用。
- 两个工具的安装记录完整。

## 5. 阶段 3：选择 Java/Vue 仓库

负责人：测评负责人

任务：

1. 从内网离线仓库中选择：

- 1 个 Java 项目
- 1 个 Vue 项目

2. 固定 commit：

```bash
git rev-parse HEAD
git status --short
```

3. 记录仓库基础信息：

```yaml
repos:
  - repo_id: java_001
    name:
    path:
    commit:
    type: java
    languages:
      - Java
    build_tool: maven | gradle | unknown

  - repo_id: vue_001
    name:
    path:
    commit:
    type: vue
    languages:
      - TypeScript
      - Vue
    package_manager: npm | pnpm | yarn | unknown
```

产物：

```text
benchmark-cg-gn/repos/repos-manifest.yaml
```

选仓建议：

- 不要选择太小的 demo 项目。
- 不要选择无法正常索引的大型怪异项目作为第一轮。
- Java 项目最好有 controller/service/repository 或类似分层。
- Vue 项目最好有 router、views/pages、components、api/store。

验收标准：

- 两个仓库路径明确。
- commit 已冻结。
- 工作区状态已记录。

## 6. 阶段 4：生成仓库画像、任务和参考事实

负责人：测评执行人

每个仓库独立执行。

### 6.1 生成 repo-profile

用内部 agent，不使用 `codegraph` 和 `GitNexus`。

输出：

```text
benchmark-cg-gn/repo-results/<repo_id>/repo-profile.yaml
```

Java 项目画像重点：

- build tool
- main module
- package structure
- controller/service/repository
- config files
- entrypoints
- test commands

Vue 项目画像重点：

- package manager
- Vite/Vue CLI/Nuxt 等框架
- router
- views/pages
- components
- store
- api/request 封装
- entrypoints

### 6.2 生成 tasks.yaml

每个仓库 6 个任务。

Java 项目建议任务：

1. 宏观架构：模块、分层、入口。
2. 请求链路：从 controller 或 API 入口到 service/repository。
3. 依赖关系：核心业务模块依赖哪些基础设施。
4. 影响分析：修改某个 service/interface/config 的影响。
5. onboarding：新人阅读顺序。
6. 风险模块：哪些类或包最容易影响全局。

Vue 项目建议任务：

1. 宏观架构：页面、组件、状态、API、路由。
2. 启动链路：从 `main.ts/js` 到 router/store/app mount。
3. 页面到 API 链路：页面如何调用请求封装。
4. 影响分析：修改请求封装、router、store 的影响。
5. onboarding：新人阅读顺序。
6. 风险模块：哪些文件或模块最容易影响全局。

输出：

```text
benchmark-cg-gn/repo-results/<repo_id>/tasks.yaml
```

### 6.3 构建 reference-facts

参考事实不要求人工熟悉仓库，但必须有证据。

输出：

```text
benchmark-cg-gn/repo-results/<repo_id>/reference-facts.yaml
```

每个事实格式：

```yaml
fact_id: F001
type: entrypoint | module | dependency | call_chain | impact | architecture
claim: string
evidence:
  - path: string
  - command: string
confidence: high | medium | low | disputed
```

要求：

- 至少 20 条 high/medium facts。
- Java 和 Vue 都要包含入口、模块、依赖、调用/数据流、影响点。
- `low` 和 `disputed` 不进入硬评分。

验收标准：

- 每个仓有 `repo-profile.yaml`、`tasks.yaml`、`reference-facts.yaml`。
- 每个任务都能被 reference facts 部分覆盖。

## 7. 阶段 5：执行三臂测评

负责人：测评执行人

每个仓、每个任务执行 3 个实验臂：

```text
Baseline
codegraph
GitNexus
```

建议第一轮每个任务跑 1 次。如果时间允许，每个任务跑 2 次。

### 7.1 Baseline

限制：

- 只允许源码阅读、目录浏览、文本搜索。
- 禁止读取 `.codegraph/`、`.gitnexus/`、reference、其他实验臂结果。

输出目录：

```text
benchmark-cg-gn/repo-results/<repo_id>/runs/baseline/<task_id>/
  prompt.txt
  answer.md
  metrics.yaml
  command-log.txt
```

### 7.2 codegraph

准备：

```bash
cd <repo>
codegraph init -i
```

限制：

- 必须优先使用 codegraph 查询。
- 可以读取源码做校验。
- 禁止读取 `.gitnexus/`、reference、其他实验臂结果。

输出目录：

```text
benchmark-cg-gn/repo-results/<repo_id>/runs/codegraph/<task_id>/
  prompt.txt
  answer.md
  metrics.yaml
  tool-log.jsonl
  command-log.txt
```

### 7.3 GitNexus

准备：

```bash
cd <repo>
gitnexus analyze --skip-embeddings
```

限制：

- 必须优先使用 GitNexus 查询、上下文或 skills。
- 可以读取源码做校验。
- 禁止读取 `.codegraph/`、reference、其他实验臂结果。

输出目录：

```text
benchmark-cg-gn/repo-results/<repo_id>/runs/gitnexus/<task_id>/
  prompt.txt
  answer.md
  metrics.yaml
  tool-log.jsonl
  command-log.txt
```

### 7.4 必须记录的 metrics

```yaml
arm:
task_id:
wall_time_seconds:
index_time_seconds:
answer_time_seconds:
file_reads:
search_calls:
shell_calls:
tool_calls:
tool_call_saving_vs_baseline:
input_tokens:
output_tokens:
total_tokens:
answer_chars:
supported_claims:
unsupported_claims:
hallucinated_claims:
notes:
```

如果无法拿到 token：

- 记录 `input_tokens: null`
- 使用文件读取数、搜索输出、工具输出长度、答案长度作为代理 token。

验收标准：

- 每个仓 6 个任务 x 3 个实验臂均有答案和 metrics。
- 工具索引失败也要记录，不允许跳过。

## 8. 阶段 6：评分和单仓报告

负责人：结果复核人

每个仓输出：

```text
benchmark-cg-gn/repo-results/<repo_id>/scores.csv
benchmark-cg-gn/repo-results/<repo_id>/repo-report.md
```

评分维度：

| 指标 | 权重 |
| --- | ---: |
| 准确率 | 35 |
| 证据质量 | 15 |
| 架构抽象 | 15 |
| 幻觉控制 | 10 |
| 效率 | 10 |
| 响应时间 | 10 |
| token 或代理 token | 5 |

单仓报告必须包含：

1. 仓库信息。
2. 工具索引是否成功。
3. 任务列表。
4. 三臂总分对比。
5. 分任务得分。
6. 准确率观察。
7. 效率和响应时间观察。
8. token 或代理 token 观察。
9. 典型成功案例。
10. 典型失败或争议案例。
11. 本仓结论。

验收标准：

- Java 项目有完整 `repo-report.md`。
- Vue 项目有完整 `repo-report.md`。
- 每个结论都有答案或 metrics 证据。

- 平均 tool calls 是否减少，减少的是无效探索，还是用工具调用替代了文件读取。
- 哪个工具更适合作为下一阶段主线。
- 是否需要继续测 `GitNexus + codegraph` 组合臂。

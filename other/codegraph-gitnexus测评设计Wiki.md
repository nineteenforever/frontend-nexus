# codegraph 与 GitNexus 架构识别测评设计

> 这是一份面向分享和评审的测评设计说明。目标是让读者在几分钟内理解：我们想测什么、怎么测，以及为什么这套结果相对真实可靠。

## 1. 我们想回答什么问题

这次测评不是比较工具宣传页上的功能数量，也不是验证工具能不能在一个 demo 项目里回答问题。

我们真正想回答的是：

```text
当研发人员不熟悉一个真实代码仓库，只能依靠内网 agent 和本地源码时，
codegraph 和 GitNexus 相对普通源码阅读，能否更准确、更高效地识别代码架构？
```

这里的“更好”需要可以量化，而不是只看答案是否流畅。

我们关注：

- 架构结论是否准确
- 结论是否有源码证据
- agent 是否减少文件阅读和搜索
- 响应时间是否缩短
- tool calls、token 或代理 token 是否节约
- 工具建立索引和刷新索引的成本是否值得

## 2. 测评背景

本轮由多位执行人员对同一组 5 个真实代码仓进行交叉测评：

| 项目类型 | 仓库数量 |
| --- | ---: |
| Java | 2 |
| Vue | 3 |
| 合计 | 5 |

所有仓库源码都已经放在内网本地环境中。执行人员不需要提前熟悉项目，也不依赖公网文档。

这个场景接近实际工作：

- 新人接手陌生项目
- agent 首次进入一个代码仓
- 研发需要快速理解入口、模块、依赖和改动影响
- 内网环境不能依赖外部搜索

每个仓库都以 Baseline 为基准，执行三组独立实验：

| 实验臂 | 使用方式 | 想验证什么 |
| --- | --- | --- |
| Baseline | agent 只使用普通文件读取、目录浏览、文本搜索和 git 基础命令 | 不使用架构工具时，agent 自己能做到什么程度 |
| codegraph | agent 优先使用 codegraph，再读取源码校验 | codegraph 相对 Baseline 提升了什么 |
| GitNexus | agent 优先使用 GitNexus，再读取源码校验 | GitNexus 相对 Baseline 提升了什么 |

Baseline 是整个设计的关键。如果没有 Baseline，我们只能知道工具“能回答”，但无法知道这些答案是不是 agent 原本就能找到，也无法判断工具是否真的节省了探索成本。

```text
工具收益 = 工具实验臂结果 - Baseline 结果
```

## 3. 测评流程

![codegraph 与 GitNexus 架构识别单仓测评流程](./assets/codegraph-gitnexus-evaluation-workflow.png)

整套测评分为四个阶段。前三个阶段完成单仓测评，第四个阶段负责把多个仓库的结果复核并汇总成最终报告。

### 3.1 阶段 1：主 agent 准备测评

主 agent 首先完成测评准备：

1. 检查环境和可用工具，区分 codegraph、GitNexus 和普通工具。
2. 识别仓库画像，包括语言、框架、文件数、代码行数、分支和 commit。
3. 根据仓库实际结构生成 6 类架构识别任务。
4. 基于源码、配置、README、测试和构建文件，构建带证据的参考事实。
5. 建立 codegraph 和 GitNexus 索引，并记录首次索引和刷新成本。

仓库画像用于解释不同项目之间的结果差异。一个 5 万行 Java 项目和一个 20 万行 Vue 项目，工具表现不能简单放在一起比较。

#### 6 类架构识别任务

架构识别不是单一能力。一个工具可能擅长找调用链，但不擅长解释模块职责；也可能生成了漂亮总结，却缺少可靠证据。

因此每个仓库都覆盖 6 类典型任务：

| 任务类型 | 要验证的能力 | 示例问题 |
| --- | --- | --- |
| 整体架构识别 | 识别模块、分层、入口和协作关系 | “请说明当前仓库的整体架构、主要模块、分层关系和关键入口。” |
| 入口流程识别 | 从入口追踪到核心运行流程 | “从应用启动入口开始，核心请求或页面初始化流程经过哪些模块？” |
| 依赖关系识别 | 识别模块之间的依赖方向 | “核心业务模块依赖哪些基础模块？是否存在反向依赖或跨层调用？” |
| 影响范围分析 | 判断改动核心文件会影响哪里 | “如果修改用户权限服务或请求封装模块，可能影响哪些入口和功能？” |
| 新人阅读顺序 | 形成有效的代码阅读路径 | “如果新人要理解这个项目，建议按什么顺序阅读哪些目录和文件？” |
| 架构风险识别 | 找出影响全局的关键模块和风险点 | “哪些模块最容易形成单点风险、耦合风险或大范围改动影响？” |

任务类型在不同仓库之间保持一致，但具体问题必须结合当前仓库的真实入口、模块和文件生成。这样既能跨仓比较，也不会用一套固定问题生搬硬套所有项目。

#### 参考事实为什么重要

执行人员不熟悉仓库，也没有提前准备好的标准答案。为了让后续评分有依据，主 agent 会先建立一组带源码证据的参考事实。

例如：

```yaml
claim: 用户请求由 UserController 进入，并调用 UserService。
evidence:
  - src/main/java/.../UserController.java
  - src/main/java/.../UserService.java
confidence: high
```

参考事实只在评分阶段使用。正式运行 Baseline、codegraph 和 GitNexus 时，三个实验臂都不能读取它。

### 3.2 阶段 2：主 agent 编排三臂独立运行

主 agent 按任务队列编排运行。每个任务都分别执行：

```text
Baseline
codegraph
GitNexus
```

单仓测评手册没有强制要求必须使用 subagent。实际执行时可以由主 agent 自己逐个运行，也可以由主 agent 将独立 case 发布给 subagent。无论采用哪种方式，三个实验臂都必须保持隔离。

| 实验臂 | 允许 | 禁止 |
| --- | --- | --- |
| Baseline | 普通源码阅读、目录浏览、文件读取、文本搜索 | codegraph、GitNexus、参考事实、其他实验臂结果 |
| codegraph | codegraph 查询、必要的源码校验 | GitNexus、参考事实、其他实验臂结果 |
| GitNexus | GitNexus 查询、必要的源码校验 | codegraph、参考事实、其他实验臂结果 |

如果某个实验臂使用了禁止工具，或读取了其他实验臂结果，该 case 会被标记为隔离污染，不能进入主评分。

#### 什么是源码校验

源码校验不是让工具实验臂重新做一遍 Baseline，也不是读取参考事实。

它表示：

```text
工具给出结构、入口、调用链或依赖结论后，
agent 读取对应源码，确认文件、符号和关系真实存在。
```

例如 codegraph 发现 `UserController -> UserService`，agent 可以打开这两个文件，确认类和调用关系确实存在。这样可以避免把工具索引错误直接写进最终答案。

#### 每个 case 记录什么

每个任务、每个实验臂都会保存答案、指标和工具日志。主要记录：

| 记录项 | 含义 |
| --- | --- |
| `answer` | 当前实验臂对任务的完整回答 |
| `answer_time_seconds` | 从开始执行任务到输出答案的时间，不含索引时间 |
| `file_reads` | 为回答问题读取源码文件的次数 |
| `search_calls` | 使用文本搜索的次数 |
| `shell_calls` | 使用普通命令行工具的次数 |
| `tool_calls` | 调用 codegraph、GitNexus 或其他专用工具的次数 |
| `total_tokens` | 可获取时记录真实 token |
| 代理 token 指标 | 无法获取真实 token 时，记录读取文件、搜索输出、工具输出和答案长度 |
| `supported_claims` | 有源码或工具证据支撑的结论数量 |
| `unsupported_claims` | 缺少证据支撑的结论数量 |
| `hallucinated_claims` | 虚构文件、符号、模块或关系的数量 |
| `evidence_count` | 回答中可复核证据的数量 |
| `tool-log` | 实际调用过的命令、MCP 工具和读取文件 |
| 隔离状态 | 是否误用禁止工具或读取其他实验臂结果 |

阶段 2 只负责独立运行并保存原始结果，不在每个 case 返回时立即评分。

### 3.3 阶段 3：统一评分与单仓报告

当所有有效 case 完成后，主 agent 才进入统一评分阶段。

评分阶段允许读取：

- Baseline、codegraph、GitNexus 三个实验臂的答案和指标
- 阶段 1 构建的 `reference-facts`
- 每个 case 保存的源码证据和工具日志

每个任务满分 100 分：

| 评分维度 | 权重 | 关注点 |
| --- | ---: | --- |
| 准确率 | 35 | 关键架构结论是否正确 |
| 证据质量 | 15 | 是否能用真实文件、符号、调用或依赖关系支撑 |
| 架构抽象 | 15 | 是否能从代码细节总结合理的模块、职责和协作关系 |
| 幻觉控制 | 10 | 是否避免虚构不存在的文件、模块或调用关系 |
| 效率 | 10 | 是否减少文件读取、搜索和不必要的探索步骤 |
| 响应时间 | 10 | 完成任务是否更快 |
| token 或代理 token | 5 | 是否减少上下文读取和输出成本 |

评分后，以 Baseline 为参照计算工具增益：

```text
质量增益
回答时间节约
文件读取节约
搜索次数节约
tool calls 节约
token 或代理 token 节约
```

同时单独评价索引成本：

```text
回答时间：索引完成后，回答一个任务需要多久
端到端时间：首次索引时间 + 回答时间
摊销时间：索引成本分摊到多个架构任务后的平均成本
```

这可以避免出现“回答阶段很快，但首次索引非常慢”的工具被高估。

单仓报告最终展示：

- 仓库语言、文件数、代码行数和规模
- 三个实验臂的质量分和效率指标
- codegraph / GitNexus 相对 Baseline 的增益
- 首次索引和代码变化后的刷新成本
- 实验臂隔离情况
- 典型成功案例和失败案例

### 3.4 阶段 4：多仓复核与最终报告

所有单仓测评完成后，再统一做多仓复核：

1. 汇集多个仓库的单仓结果。
2. 检查结果完整性、实验臂隔离情况和异常值。
3. 从原始评分数据重新计算汇总指标，而不是直接相信单仓报告中的汇总表。
4. 抽样检查答案中的源码证据是否真实存在。
5. 按语言、项目类型和规模聚合结果。
6. 生成最终交叉测评报告。

这个阶段不依赖具体有多少位执行人员。它的重点是用统一口径复核所有仓库，避免把单仓偏差或不完整结果直接带入最终结论。

## 8. 如何阅读最终报告

最终报告中的结论建议按下面顺序阅读：

1. 先看样本范围：语言、仓库规模、有效样本数。
2. 再看质量增益：工具是否比 Baseline 更准确。
3. 再看效率增益：时间、文件读取、搜索、tool calls、token 是否改善。
4. 再看索引成本：首次使用和代码变化后的维护成本。
5. 最后看典型案例：工具在哪些任务上真正有帮助，在哪些任务上容易失败。

不要只看一个平均分。一个工具可能总体平均不错，但只在 Java 上有效；也可能回答阶段很快，但首次索引成本很高。

## 9. 设计边界

这套测评设计相对真实可靠，但仍有边界：

- 当前样本只有 5 个仓库，不能代表所有 Java 和 Vue 项目。
- 不同仓库的业务复杂度、框架版本和代码质量不同。
- 参考事实由 agent 构建，仍可能存在遗漏，需要抽样复核。
- 不同模型、不同 agent 配置可能产生不同结果。
- 本轮结论适用于“架构识别”场景，不直接等同于代码生成、缺陷修复或代码审查能力。

因此最终结论应理解为：

```text
在当前内网 agent、当前真实仓库样本和当前架构识别任务下，
codegraph 与 GitNexus 相对 Baseline 的实操表现。
```

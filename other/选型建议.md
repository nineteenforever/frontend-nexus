# AI 架构识别工具选型建议

## 0. 结论先行

如果当前目标是做“面向 AI 开发助手的代码架构理解产品”，我建议优先选择：

```text
GitNexus + codegraph
```

但这个组合不能理解成“两个代码图谱工具一起开”。它们确实有重合：都会做代码索引、关系抽取、调用链、影响分析、MCP/agent 接入。真正合理的用法是分层：

```text
codegraph = 可信代码结构底座
GitNexus = 面向 agent 的产品化工作流增强层
```

一句话：

> 用 `codegraph` 保证 agent 看到的代码关系尽可能准确、实时、可评测；用 `GitNexus` 把这些结构能力变成 agent 更容易使用的上下文、技能、工作流和产品体验。

如果只选一个，我仍然建议先选 `codegraph` 做底座；如果要做产品，而不是只做评测工具，则建议组合 `GitNexus + codegraph`。

## 1. 为什么不直接只选 GitNexus

`GitNexus` 很适合做 AI 开发助手产品，因为它更关注：

- agent 如何接入
- 如何给 agent 注入上下文
- 如何生成 `AGENTS.md`、skills、工作流提示
- 如何把图谱能力包装成 AI 开发过程中的可用能力
- 如何围绕 PR review、风险分析、流程、社区做产品化

它的优势不是单个静态分析能力，而是“从索引到 agent 使用”的整条链路。

但如果只选 `GitNexus`，风险在于：

- 系统较重，组件和内部状态更多。
- 增量更新、缓存、dirty state、schema、worker、DB 写回等链路复杂。
- 如果后续要做严格 benchmark，底层事实图谱的可控性和可替换性不如 `codegraph` 简洁。
- 当目标是“先把代码结构事实做准”，它不一定是最小闭环。

所以 `GitNexus` 更适合作为产品层，而不是唯一底层。

## 2. 为什么不直接只选 codegraph

`codegraph` 更像一个扎实的代码结构引擎：

- AST / tree-sitter 抽取
- symbol / file / edge 图谱
- callers / callees / impact / context / explore
- framework-aware 补边
- 自动同步、staleness banner、MCP server
- SQLite 本地索引
- 易于 benchmark 和复现

它很适合做“AI 识别架构”的可靠底座。

但如果只选 `codegraph`，产品层会偏薄：

- 它更像基础设施，不是完整 AI 开发助手产品。
- 对 agent 的主动工作流增强不如 `GitNexus` 激进。
- 对“如何把结果变成长期上下文、模块技能、团队工作流”覆盖较少。
- 对高层产品能力，如 PR review、agent workflow、自动 context 注入，需要自己补。

所以 `codegraph` 更适合作为底层结构事实引擎，而不是完整产品终点。

## 3. 两者重合在哪里

它们的重合主要在下面几层：

| 重合点 | GitNexus | codegraph |
| --- | --- | --- |
| 代码索引 | 有 | 有 |
| 关系抽取 | 有 | 有 |
| 调用链分析 | 有 | 有 |
| 影响分析 | 有 | 有 |
| MCP 接入 | 有 | 有 |
| agent 使用 | 有 | 有 |
| 多语言支持 | 有 | 有 |

所以不要把二者都作为“同一层的图谱工具”并行使用。那样会带来：

- agent 不知道该问谁。
- 两套索引结果冲突时难以仲裁。
- 重复索引增加成本。
- 评测时无法判断收益来自哪个工具。
- 产品心智混乱。

组合使用的前提是明确分工。

## 4. 两者不重合在哪里

真正的差异在“产品层级”和“工程性格”。

| 维度 | GitNexus 更强 | codegraph 更强 |
| --- | --- | --- |
| 产品形态 | Agent-first 平台、workflow、skills、上下文注入 | 本地结构图谱、MCP 查询 |
| 底层事实可控性 | 强，但链路较复杂 | 更收敛、更易评测 |
| 增量维护体验 | 有增量，但偏重型 | 自动同步和 staleness 处理更轻 |
| agent 工作流增强 | 更强 | 更克制 |
| benchmark 友好度 | 强 | 很强 |
| 最小可用闭环 | 较重 | 较轻 |
| 长期产品扩展 | 更像产品平台 | 更像引擎底座 |

可以这样理解：

```text
codegraph 解决：代码事实是什么？
GitNexus 解决：agent 怎么把这些事实用进开发工作流？
```

## 5. 推荐架构：codegraph 底座 + GitNexus 产品层

推荐架构：

```text
源码仓库
  |
  |-- codegraph
  |     |-- AST / symbol / edge / callers / callees / impact
  |     |-- freshness / sync / local SQLite
  |     |-- MCP tools
  |
  |-- GitNexus
        |-- agent context
        |-- skills / AGENTS.md / workflow prompts
        |-- augment / hooks
        |-- PR review / risk / flow / community
        |-- product UI / agent orchestration
```

更理想的长期方向：

```text
codegraph 输出可信结构事实
        ↓
GitNexus 消费或对齐这些事实
        ↓
内部 agent 使用 GitNexus 风格的工作流入口
        ↓
关键事实查询回落到 codegraph
```

也就是说，用户和 agent 面对的是一个统一产品入口，但底层结构事实尽量由 `codegraph` 承担。

## 6. Agent 应该怎么用二者

不要让 agent 无限制地同时问两个工具。建议定义路由规则。

### 6.1 默认问 codegraph 的场景

这些任务优先使用 `codegraph`：

- 某个函数/类/组件在哪里定义。
- 谁调用了某个函数。
- 某个函数调用了谁。
- 从入口到目标符号的路径是什么。
- 修改某个文件或符号的影响范围。
- 某个文件是否过期、图谱是否 fresh。
- 需要可验证、可复现、低幻觉的结构事实。

Prompt 规则：

```text
当问题需要确定的调用关系、依赖关系、影响范围、入口链路时，优先使用 codegraph。
如果 codegraph 结果不足，再用源码阅读补证据。
```

### 6.2 默认问 GitNexus 的场景

这些任务优先使用 `GitNexus`：

- 让 agent 快速理解某个业务区域。
- 生成模块级上下文。
- 需要 area skill、AGENTS.md、工作流提示。
- PR review 或风险分析。
- 需要结合社区、流程、风险、执行路径的开发助手体验。
- 需要在 IDE/agent 工作流里自动增强搜索结果。

Prompt 规则：

```text
当问题需要面向开发任务组织上下文、生成工作流建议、做 PR 风险分析或给 agent 注入模块知识时，优先使用 GitNexus。
关键结构事实需要用 codegraph 或源码二次校验。
```

### 6.3 二者都用的场景

这些任务适合组合：

- “我要改登录流程，帮我理解影响范围并给出修改计划。”
- “这个 PR 会影响哪些模块，风险在哪里？”
- “新人要接手支付模块，先看哪些文件，哪些调用链最关键？”
- “agent 准备改一个核心接口，先生成安全修改计划。”

组合顺序：

```text
1. GitNexus 先给模块/工作流/风险/上下文视角
2. codegraph 校验关键调用链、依赖边、影响半径
3. agent 读取少量源码验证争议点
4. 输出最终计划，并标记证据来源
```

## 7. 组合使用时的冲突处理

如果 `GitNexus` 和 `codegraph` 对同一个关系给出不同结论，建议按以下优先级：

1. 源码直接证据最高。
2. 编译器、测试、语言服务器、AST 解析结果次之。
3. `codegraph` 的 callers/callees/impact/context 结果作为结构事实优先。
4. `GitNexus` 的社区、流程、风险、agent context 作为高层解释优先。
5. LLM 语义推断最低，必须标记不确定。

简单规则：

```text
事实关系听 codegraph；
工作流组织听 GitNexus；
最终结论必须能回到源码证据。
```

## 8. 产品化路线建议

### 阶段 1：先用 codegraph 建立可信底座

目标：

- 完成内网安装。
- 跑通 MCP。
- 对 3 个仓库建立 `.codegraph/`。
- 验证 `context`、`callers`、`callees`、`impact`。
- 建立基础评测集。

验收标准：

- agent 能稳定回答“入口、调用链、影响范围”。
- 大仓库中比 Baseline 少读文件、少搜索。
- 每个结论都有文件或符号证据。

### 阶段 2：引入 GitNexus 做 agent 工作流增强

目标：

- 跑通 `gitnexus analyze`。
- 接入 MCP。
- 生成 agent context 和 skills。
- 验证 augment / hooks / workflow 对开发任务的帮助。

验收标准：

- agent 处理开发任务时更快定位模块。
- 生成的上下文能减少冷启动。
- PR review / risk / flow 类任务明显优于纯 codegraph。

### 阶段 3：做统一工具路由

目标：

- 不让 agent 随机选择工具。
- 用 prompt 或内部 router 固定工具职责。
- 记录每次工具调用的贡献。

建议路由：

| 用户问题 | 优先工具 | 校验工具 |
| --- | --- | --- |
| 谁调用了 X | codegraph | 源码 |
| 改 X 影响谁 | codegraph | GitNexus 风险视角 |
| 这个模块负责什么 | GitNexus | codegraph + 源码 |
| PR 风险是什么 | GitNexus | codegraph impact |
| 新人怎么读 | GitNexus | codegraph 入口/依赖 |
| 架构总览 | GitNexus | codegraph 结构证据 |

### 阶段 4：沉淀成内部 AI 开发助手产品

目标：

- 对用户只暴露一个“架构助手”入口。
- 底层根据任务自动调用 GitNexus 或 codegraph。
- 输出统一证据格式。
- 支持 PR、代码修改、onboarding、影响分析、架构问答。

统一输出格式：

```yaml
answer:
  summary: string
  modules: []
  call_chains: []
  impact: []
  risks: []
  suggested_plan: []
evidence:
  codegraph:
    - tool: codegraph_impact
      result_ref: ...
  gitnexus:
    - tool: gitnexus_query
      result_ref: ...
  source:
    - path: src/...
      symbol: ...
uncertainty:
  - string
```

## 9. 不建议的组合方式

不要这样用：

```text
agent 同时安装 GitNexus 和 codegraph
然后让 agent 自己想用哪个就用哪个
```

这会导致：

- 工具调用不可控。
- 结论来源不可解释。
- 两套图谱冲突时没有规则。
- benchmark 结果无法归因。

也不要一开始就强行把两者底层索引融合。早期更好的方式是：

```text
先并行安装
再明确路由
再记录冲突
最后决定是否做统一抽象层
```

## 10. 是否需要二选一

短期评测需要二选一，产品建设不一定。

评测阶段建议分开：

- `codegraph` 单独一组。
- `GitNexus` 单独一组。
- `GitNexus + codegraph` 作为组合组，单独评测。

这样才能回答：

1. `codegraph` 自己能提升多少。
2. `GitNexus` 自己能提升多少。
3. 两者组合是否真的比单工具更好。
4. 组合提升是否值得额外复杂度。

产品阶段可以合并：

- 用户不需要知道底层用了几个工具。
- agent 也不应该自由乱选。
- 内部 router 根据任务选择工具。

## 11. 推荐评测补充

在原有 5 个实验臂基础上，加一个组合实验臂：

```text
Baseline
GitNexus
codegraph
graphify
Understand-Anything
GitNexus + codegraph
```

组合臂规则：

```text
1. 优先用 GitNexus 获取模块上下文、工作流视角和风险视角。
2. 对所有调用链、依赖关系、影响范围，必须用 codegraph 或源码校验。
3. 最终答案必须标注每条关键结论来自 GitNexus、codegraph 还是源码。
4. 如果两者冲突，必须显式记录冲突和仲裁依据。
```

组合臂重点看：

- 是否比单独 `codegraph` 更会组织任务。
- 是否比单独 `GitNexus` 更低幻觉。
- 是否减少 agent 冷启动和无效搜索。
- 是否增加过多安装、索引、维护复杂度。

## 12. 最终建议

我的建议是：

```text
主线：codegraph
产品层增强：GitNexus
组合验证：GitNexus + codegraph
暂缓：graphify、Understand-Anything
```

原因：

- `codegraph` 更适合作为可评测、低幻觉、低维护成本的结构事实底座。
- `GitNexus` 更适合作为 AI 开发助手产品层，负责上下文注入、workflow、skills、风险分析。
- 二者能力有重合，但重合部分不应该简单叠加，而应该通过路由和职责边界消化。
- 如果组合组在评测中没有明显超过单独 `codegraph` 或 `GitNexus`，就先不要上组合，避免复杂度过早膨胀。

最后一句判断：

> 如果你要做“可靠的架构识别能力”，先上 `codegraph`；如果你要做“让内部 agent 在开发中持续理解仓库的产品”，在 `codegraph` 底座上叠 `GitNexus`。

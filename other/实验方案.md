# AI 辅助识别代码架构实验方案

## 1. 实验目标

本实验不是单纯比较“哪个工具功能多”，而是要回答下面 4 个核心问题：

1. 不借助专门工具时，agent 单靠源码阅读，识别代码架构的效果基线是多少。
2. 引入 `GitNexus`、`graphify`、`Understand-Anything`、`codegraph` 后，架构识别质量分别提升多少。
3. 这些提升在**小型、中型、大型仓库**上是否稳定。
4. 不同模型、不同轮次、不同任务类型下，哪种方案的收益最大、最稳、最划算。

## 2. 总体实验设计

### 2.1 对照组与实验组

定义 5 个实验臂（arms）：

- `Baseline`：不用任何专门工具，agent 只可使用最基础能力，如目录浏览、文件读取、关键词搜索。
- `GitNexus`：先对仓库建索引，再允许 agent 使用其 CLI/MCP/上下文增强能力。
- `graphify`：先构建图谱，再允许 agent 使用其查询或导出结果。
- `Understand-Anything`：先生成知识图和 dashboard/相关产物，再让 agent 基于这些结果分析。
- `codegraph`：先建立代码图谱索引，再允许 agent 使用其 CLI/MCP 高层查询接口。

### 2.2 分层变量

实验至少在 3 个维度分层：

- **仓库规模**
  - 小型：1k 到 10k LOC
  - 中型：10k 到 100k LOC
  - 大型：100k LOC 以上
- **模型类型**
  - 强推理模型
  - 中等成本模型
  - 开源模型
- **任务类型**
  - 静态架构识别
  - 调用链/依赖分析
  - 业务流程还原
  - 影响范围分析
  - onboarding 解释任务

### 2.3 实验原则

- 所有实验臂使用同一批仓库、同一批问题集、同一批评分标准。
- 对每个任务进行多轮重复，降低偶然性。
- 基线组和工具组的唯一差异应是“是否可使用对应方案产出的中间表示和接口”。
- 评测分为**离线客观指标**和**人工主观指标**两层。

## 3. 仓库选样方案

建议每个规模至少 3 个仓库，合计最少 9 个仓库。

### 3.1 小型仓库

要求：

- 模块数有限
- 结构相对清晰
- 方便人工建立高质量真值

建议类型：

- 单体后端小服务
- 中小型前端应用
- CLI 工具

建议数量：

- 3 个

### 3.2 中型仓库

要求：

- 有明确分层
- 有跨目录依赖
- 有一定框架特征

建议类型：

- Web 服务
- React/Vue 前端
- SDK/库项目

建议数量：

- 3 个

### 3.3 大型仓库

要求：

- 多模块、多包、多语言或复杂框架
- 人工完整通读成本高
- 能体现工具的真正收益

建议类型：

- Monorepo
- 框架源码
- 多服务平台

建议数量：

- 3 个

### 3.4 样本选择原则

- 不要只选自己熟悉的仓库，避免人为偏置。
- 尽量覆盖不同语言和框架，如 TypeScript、Python、Go、Java。
- 尽量选择有 README、架构说明、测试、配置文件的真实项目。
- 尽量保证开源活跃、结构完整、可本地运行或至少可成功索引。

## 4. 真值构建

没有真值，就无法真正比较“识别架构”的效果。

### 4.1 真值内容

每个仓库需要提前制作一份 `ground truth`，建议包含：

- 系统模块列表
- 每个模块的一句话职责
- 模块之间的主要依赖关系
- 关键入口点
- 3 到 5 条典型调用链
- 2 到 3 个核心业务流程
- 关键基础设施组件
- 架构分层结论

### 4.2 真值来源

真值不应只来自 README，应采用“多源合成”：

- 官方文档
- 代码结构
- 配置文件
- 测试
- issue / PR / design note
- 至少 2 名评审者独立整理后合并

### 4.3 真值制作方法

建议流程：

1. 由资深工程师先阅读仓库并出第一版真值。
2. 第二名评审者独立复核。
3. 对争议项做合并与记录。
4. 对每个仓库保留“高确定性真值”和“低确定性开放项”。

开放项不纳入硬性扣分，只用于补充讨论。

## 5. 任务设计

建议每个仓库至少 8 到 12 个任务，覆盖不同层级。

### 5.1 一级任务：宏观架构识别

示例：

- 这个仓库的整体架构是什么？
- 主要模块有哪些？分别负责什么？
- 系统的分层是什么？
- 数据流或请求流大致如何流动？

### 5.2 二级任务：关系与路径识别

示例：

- 从某个入口到核心处理逻辑的调用路径是什么？
- 某个模块依赖了哪些上游/下游模块？
- 某个 API endpoint 最终调用了哪些关键组件？
- 某个功能涉及哪些文件和符号？

### 5.3 三级任务：语义与抽象

示例：

- 为什么这个模块被拆成这样？
- 哪些模块属于基础设施层，哪些属于业务层？
- 这个项目的核心领域概念是什么？
- 新人理解这个仓库，应该按什么顺序阅读？

### 5.4 四级任务：变更与影响分析

示例：

- 如果修改某个核心函数，潜在影响范围是什么？
- 哪些模块会受某个 schema / interface 变化影响？
- 某个配置项改变会影响哪些路径？

### 5.5 任务难度分级

对每个任务标记难度：

- `L1`：局部、可直接定位
- `L2`：需要跨文件整合
- `L3`：需要模块级抽象
- `L4`：需要系统级归纳和解释

## 6. Prompt 与执行控制

### 6.1 基线组 Prompt

基线组只能用普通能力，不能引用任何专门工具产物。

示例提示词：

```text
请分析这个代码仓库的架构。
你只能使用目录浏览、文件读取和文本搜索，不允许使用任何预构建图谱、知识库、索引系统或外部总结。
请给出：
1. 模块划分
2. 分层关系
3. 关键入口
4. 主要调用链
5. 你的不确定点
```

### 6.2 工具组 Prompt

工具组要控制为“可用对应工具，但不能多用其他组工具”。

示例提示词：

```text
请分析这个代码仓库的架构。
你应优先使用当前允许的工具产物和接口完成分析，再用必要的源码阅读进行验证。
请给出：
1. 模块划分
2. 分层关系
3. 关键入口
4. 主要调用链
5. 你的不确定点
6. 工具帮助你发现了哪些基线组难以发现的信息
```

### 6.3 执行约束

- 每轮实验限制最大上下文窗口消耗或 token 预算。
- 每轮限制最大执行时间。
- 记录工具调用次数。
- 记录读文件数、搜索次数、图查询次数。
- 若允许联网，所有组必须一致；更推荐完全离线。

## 7. 指标体系

建议把评测拆成 7 类指标。

### 7.1 架构识别准确率

衡量 agent 是否识别出真实模块、层次和关系。

子指标：

- 模块识别 precision
- 模块识别 recall
- 依赖关系 precision
- 依赖关系 recall
- 关键入口识别准确率

### 7.2 调用链恢复质量

衡量 agent 对跨文件、跨模块路径的恢复能力。

子指标：

- 调用链完整率
- 调用链正确率
- 最短路径偏差
- 中间关键节点命中率

### 7.3 架构抽象质量

衡量输出是否只是“列文件”，还是已经上升到架构层。

可人工 1 到 5 分评分：

- 分层是否清晰
- 模块职责是否准确
- 表达是否压缩而不失真
- 是否能解释“为什么这样设计”

### 7.4 影响分析质量

衡量 agent 对变更影响面的判断。

子指标：

- 影响模块命中率
- 漏报率
- 误报率
- 是否能指出关键断点

### 7.5 成本指标

衡量这套方案是否“值得”。

子指标：

- 总耗时
- 建索引耗时
- 单任务平均耗时
- token 消耗
- LLM 调用次数
- 本地资源占用

### 7.6 稳定性指标

同一任务重复多轮是否稳定。

子指标：

- 同任务多轮输出一致性
- 多模型之间排序一致性
- 大中小仓库之间波动幅度

### 7.7 可用性指标

从真实团队落地角度判断。

子指标：

- 安装复杂度
- 运行成功率
- 索引失败率
- 增量更新支持
- 结果可解释性

## 8. 评分方法

建议总分 100 分，采用加权评分。

| 一级指标 | 权重 |
| --- | --- |
| 架构识别准确率 | 25 |
| 调用链恢复质量 | 20 |
| 架构抽象质量 | 15 |
| 影响分析质量 | 15 |
| 成本指标 | 10 |
| 稳定性指标 | 10 |
| 可用性指标 | 5 |

### 8.1 归一化方法

- 客观指标统一归一化到 0 到 100
- 人工评分题采用 1 到 5 分，再换算为百分制
- 多评审者取均值，并记录标准差

### 8.2 基线对比增益

最终不只看绝对分，还要看相对基线增益：

`Gain(tool) = Score(tool) - Score(baseline)`

### 8.3 性价比指标

建议引入：

`ROI = Gain / Cost`

其中 `Cost` 可综合以下项：

- 建索引耗时
- 每任务附加耗时
- token 成本
- 失败重试成本

## 9. 多轮测试设计

### 9.1 重复次数

每个“仓库 x 模型 x 实验臂 x 任务”至少跑 3 轮。

更稳妥的方案：

- 小型仓库：3 轮
- 中型仓库：3 轮
- 大型仓库：5 轮

### 9.2 多模型设计

建议至少覆盖 3 类模型：

- `High-end`：强推理模型
- `Mid-tier`：成本适中模型
- `Open-weight`：可本地或低成本部署模型

目的：

- 看工具是不是只对强模型有效
- 看工具能否弥补中等模型的能力不足
- 看工具和模型之间是否存在耦合偏置

### 9.3 温度与随机性

- 评测默认用低温度
- 如模型不可控，则记录 seed 或尽量记录版本
- 所有实验臂参数保持一致

## 10. 推荐实验矩阵

最小可行矩阵：

- 9 个仓库
- 5 个实验臂
- 3 个模型
- 每仓库 8 个任务
- 每任务 3 轮

总运行次数：

`9 x 5 x 3 x 8 x 3 = 3240`

如果成本过高，可拆为两阶段：

### 阶段一：筛选

- 3 个仓库
- 5 个实验臂
- 2 个模型
- 每仓库 6 个任务
- 每任务 2 轮

先看方向性结果。

### 阶段二：正式评测

- 扩大到 9 个仓库
- 补足 3 个模型
- 提高到每任务 3 到 5 轮

## 11. 日志与产物要求

每次实验必须保存：

- 仓库版本号
- 提示词
- 模型名称与版本
- 工具版本
- 所有工具调用日志
- 最终答案
- 执行耗时
- 失败原因

建议目录结构：

```text
benchmark/
  repos/
  prompts/
  ground-truth/
  runs/
    <repo>/<model>/<arm>/<round>/
      config.json
      prompt.txt
      tool-log.json
      final-answer.md
      metrics.json
  scoring/
  reports/
```

## 12. 评审流程

### 12.1 自动评分

适合的项：

- 模块命中率
- 关系命中率
- 调用链节点命中率
- 耗时、token、调用次数

### 12.2 人工评分

适合的项：

- 架构解释是否可信
- 分层是否有洞察
- 是否指出真正关键模块
- 是否适合新人理解

### 12.3 双盲建议

人工评分时，建议隐藏实验臂名称，只保留答案内容，避免评审者偏见。

## 13. 每种方案的特别观察点

### 13.1 Baseline

重点观察：

- agent 是否只能停留在目录/文件级总结
- 是否容易遗漏跨模块关系
- 在大仓库上是否迅速退化

### 13.2 GitNexus

重点观察：

- 社区、流程、augment 对回答质量提升有多大
- 相比基线是否减少无效读文件
- 在多轮问答中是否更稳定

### 13.3 graphify

重点观察：

- 多模态资料是否真的提升“架构语义理解”
- 图谱里文档信息是否会引入噪声
- 结构问题与语义问题上它的收益是否不同

### 13.4 Understand-Anything

重点观察：

- layer、tour、domain graph 是否提升高层解释质量
- 在 onboarding 类任务上是否显著优于其他方案
- 语义分批是否提升中大型仓库的稳定性

### 13.5 codegraph

重点观察：

- trace/context/explore 是否显著提升调用链和影响分析
- framework-aware、dynamic-dispatch 补边是否能减少断链
- 在大型仓库上的性价比是否最好

## 14. 预期结果假设

在正式实验前，可以提出可检验假设：

- `H1`：四种工具方案在中大型仓库上都会显著优于 `Baseline`
- `H2`：`codegraph` 在调用链恢复与影响分析上得分最高
- `H3`：`Understand-Anything` 在 onboarding 与高层讲解任务上得分最高
- `H4`：`graphify` 在引入文档/设计资料后，对语义解释类任务提升最大
- `H5`：`GitNexus` 在 agent 多轮交互效率上优于其他方案

## 15. 最终报告应该长什么样

正式实验完成后，建议输出 4 层结果：

### 15.1 总表

- 每个实验臂的总分、基线增益、ROI

### 15.2 分规模对比

- 小/中/大型仓库分别排名

### 15.3 分任务类型对比

- 架构识别
- 调用链分析
- 影响分析
- onboarding
- 语义解释

### 15.4 分模型对比

- 强模型是否仍需要工具
- 中模型是否更依赖工具
- 开源模型是否因工具而显著受益

## 16. 建议的最小落地版本

如果你现在资源有限，我建议先跑一个 `MVP benchmark`：

- 仓库：3 个
- 实验臂：5 个
- 模型：2 个
- 每仓库任务：6 个
- 每任务轮次：2 轮

优先关注 4 个指标：

- 架构识别准确率
- 调用链恢复质量
- 单任务耗时
- 人工主观可用性

这个 MVP 足够回答一个关键问题：

**“这些工具相对不用工具，到底有没有稳定增益，以及增益主要出现在哪类任务上。”**

## 17. 你们团队执行时的角色分工建议

- `实验设计者`：维护 prompt、协议、评分标准
- `执行 agent/执行人`：按统一流程运行实验
- `真值维护者`：维护 ground truth
- `评分者`：做双盲人工评审
- `分析者`：汇总指标、画图、出结论

## 18. 最后的建议

做这个实验时，最重要的不是追求一次跑全，而是保证三件事：

1. 基线必须严格。
2. 真值必须可信。
3. 工具收益要拆分到“准确率、效率、稳定性、成本”四个维度看。

只有这样，最后得出的“哪个更好”才不是主观印象，而是一个可以复现、可以复查、可以向团队解释的技术选型结论。

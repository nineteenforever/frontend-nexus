# AI 辅助识别代码架构工具评测执行方案

## 0. 这份方案要解决什么

这份文档用于在内网环境评测代码架构识别工具。它同时面向两类读者：

1. 人：能快速理解为什么要做这个评测、评测什么、最后如何选型。
2. Agent：拿到仓库源码和本方案后，可以按步骤生成任务、执行实验、评分、汇总报告。

本评测比较 5 种方式：

- `Baseline`：不使用任何专门架构识别工具，agent 只靠源码阅读、目录浏览、文本搜索。
- `GitNexus`：使用 GitNexus 的索引、图谱、augment、CLI/MCP 能力。
- `graphify`：使用 graphify 构建代码/文档图谱，并让 agent 基于图谱分析。
- `Understand-Anything`：使用 Understand-Anything 生成知识图、分层、tour、domain graph 等产物。
- `codegraph`：使用 codegraph 构建本地代码知识图谱，并通过 context、trace、explore、impact 等能力分析。

评测最终要回答：

1. 不用工具时，agent 对大中小仓库的架构识别能力基线是多少。
2. 四种工具相对 Baseline 分别提升了什么：准确性、效率、稳定性、成本，还是可解释性。
3. 工具收益在哪类任务最明显：宏观架构、调用链、影响分析、onboarding、业务语义理解。
4. 工具是否能让中等模型或本地模型接近强模型不用工具的效果。
5. 哪个工具适合作为主线技术底座，哪个更适合作为补充能力。

## 1. 文档组织建议

建议保留一份主执行文档，也就是当前这份：

```text
other/架构识别工具评测执行方案.md
```

工具安装与内部 agent 接入以这份文档为准：

```text
other/实验方案工具安装.md
```

其他文档可以作为背景材料或历史分析，不建议让执行 agent 同时依赖多份实验方案，否则容易产生冲突：

| 文档 | 建议定位 |
| --- | --- |
| `架构识别工具评测执行方案.md` | 主文档，实验负责人和执行 agent 都以它为准 |
| `实验方案工具安装.md` | 工具安装、内网离线包、MCP/skill/plugin 接入、smoke test |
| `对比.md`、`GRAPH_TOOL_COMPARISON.md`、`AI_ARCHITECTURE_RECOGNITION.md` | 背景阅读，用于理解工具差异，不作为实验流程依据 |

原因：你的目标不是写两份“看起来都对”的文档，而是让内网执行者和 agent 对同一套协议达成一致。主文档应该同时包含“为什么做”和“怎么跑”。

## 2. 核心原则：不依赖人工熟悉仓库

传统 benchmark 会先由熟悉仓库的人写 `ground truth`，再让模型回答并评分。但你当前场景里，人本身不熟悉这些仓库，甚至希望评测可以由 agent 自动推进。

因此本方案不把人工真值作为前置条件，而采用：

```text
多代理独立探索
+ 证据绑定
+ 交叉一致性
+ 工具互证
+ 可验证任务
+ 抽样人工审计
= 可执行的弱真值评测体系
```

也就是说，评测不要求“人先知道正确答案”，而要求每个结论必须带证据，并通过多个独立 agent、多种工具和可运行检查来提高可信度。

本方案把真值分为三层：

| 层级 | 名称 | 来源 | 用途 |
| --- | --- | --- | --- |
| L1 | 可验证事实 | 源码、配置、测试、编译器、静态分析、工具图谱 | 用于自动评分，可信度最高 |
| L2 | 共识真值 | 多个 agent 独立分析后达成一致，且都有证据 | 用于主要质量评分 |
| L3 | 专家抽样审计 | 人只抽查争议项和最终关键结论 | 用于纠偏，不要求人完整熟悉仓库 |

## 3. 总体流程

完整评测分 8 个阶段。

```text
阶段 0：准备工具和模型
阶段 1：扫描候选仓库并分层
阶段 2：自动生成仓库画像
阶段 3：自动生成任务集
阶段 4：构建弱真值/参考答案
阶段 5：执行 Baseline 和四个工具组
阶段 6：自动评分、互评、争议仲裁
阶段 7：汇总报告和选型建议
```

每个阶段都应产出机器可读文件，方便后续 agent 接力。

推荐目录结构：

```text

```

## 4. 仓库选择与分层

评测输入不是固定的 `external-repos`，而是执行时给定的源码目录。执行 agent 只需要知道一个根目录，例如：

```text
/path/to/internal/repos
```

agent 先扫描该目录下所有 git 仓库，生成 `repos-manifest.yaml`。

仓库分层：

| 规模 | 建议 LOC | 建议文件数 | 评测目的 |
| --- | ---: | ---: | --- |
| 小型 | 1k-10k | 20-200 | 看 Baseline 是否已经足够，工具是否有额外负担 |
| 中型 | 10k-100k | 200-2,000 | 看工具对跨模块理解是否有稳定增益 |
| 大型 | 100k+ | 2,000+ | 看图谱、索引、上下文压缩是否真正有价值 |

仓库选择规则：

- 每个规模至少 3 个仓库，MVP 可先每个规模 1 个。
- 覆盖至少 3 类语言或框架。
- 固定 commit，并记录分支、提交、扫描时间。
- 仓库不要求执行人熟悉。
- 仓库不能因为某工具失败就剔除，失败要进入可用性指标。

`repos-manifest.yaml` 示例：

```yaml
repos:
  - repo_id: repo_001
    name: frontend-nexus
    path: /absolute/path/to/frontend-nexus
    commit: abc123
    size_bucket: medium
    loc: 43000
    files: 680
    languages:
      - TypeScript
      - Vue
```

## 5. 自动生成仓库画像

在出题前，先让一个 `Profiler Agent` 对每个仓库生成画像。画像不是评测答案，而是用于确定仓库适合考哪些问题。

Profiler 允许使用普通源码阅读，不使用四个被评测工具，避免先验污染。

画像内容：

```yaml
repo_id: repo_001
detected_languages:
  - TypeScript
frameworks:
  - Vue
  - Vite
package_managers:
  - pnpm
entrypoint_candidates:
  - src/main.ts
  - src/router/index.ts
module_candidates:
  - src/views
  - src/components
  - src/stores
  - src/api
  - src/utils
test_commands:
  - pnpm test
  - pnpm lint
architecture_docs:
  - README.md
  - docs/architecture.md
risk_notes:
  - 路由和状态管理可能是关键架构路径
  - API client 可能集中在 src/api
```

仓库画像只回答“这个仓库大概是什么”，不直接参与最终评分。

## 6. 自动生成任务集

任务不要求人手写。由 `Task Builder Agent` 基于仓库画像和源码自动生成。

每个仓库建议 8 个任务：

| 类型 | 数量 | 目的 |
| --- | ---: | --- |
| 宏观架构识别 | 2 | 测模块、分层、入口、职责 |
| 调用链/依赖分析 | 2 | 测跨文件、跨模块路径恢复 |
| 变更影响分析 | 2 | 测影响面判断 |
| onboarding/业务语义 | 2 | 测抽象、解释、阅读顺序 |

任务必须带可评分字段：

```yaml
task_id: repo_001_T01
repo_id: repo_001
task_type: macro_architecture
difficulty: L3
question: >
  请说明该仓库的整体架构、主要模块、分层关系、关键入口，以及这些模块如何协作。
expected_answer_shape:
  - modules
  - responsibilities
  - layers
  - entrypoints
  - dependencies
  - evidence
scoring_focus:
  - module_coverage
  - dependency_correctness
  - evidence_quality
  - abstraction_quality
```

调用链任务应尽量选择真实入口和真实目标。例如：

```yaml
task_type: call_chain
question: >
  从 src/main.ts 应用启动入口开始，到路由页面组件加载完成，中间经过哪些关键模块？
anchor_files:
  - src/main.ts
  - src/router/index.ts
```

影响分析任务应尽量选择真实文件或符号。例如：

```yaml
task_type: impact_analysis
question: >
  如果修改 src/api/request.ts 的请求封装逻辑，可能影响哪些上层模块、页面或业务流程？
anchor_files:
  - src/api/request.ts
```

## 7. 弱真值构建：不熟悉仓库时怎么评分

本方案用“参考答案池”替代单一人工 ground truth。

### 7.1 参考答案池的来源

每个仓库、每个任务先由 3 类 agent 生成参考信息：

| Agent | 允许能力 | 作用 |
| --- | --- | --- |
| `Reference-Baseline-Agent` | 只用源码阅读 | 提供无工具视角 |
| `Reference-Tool-Agent` | 可以分别使用四个工具，但不参与被评分 run | 提供工具互证视角 |
| `Reference-Verifier-Agent` | 用静态命令、测试、AST/依赖解析、搜索验证 | 提供可验证事实 |

注意：参考答案池与正式评测 run 必须隔离。正式 run 不能读取 reference 目录。

### 7.2 证据绑定

参考答案中的每个关键结论必须绑定证据：

```yaml
claim_id: C001
claim: src/router/index.ts 是前端路由入口
claim_type: entrypoint
evidence:
  - type: file_exists
    path: src/router/index.ts
  - type: import_edge
    from: src/main.ts
    to: src/router/index.ts
  - type: source_snippet
    path: src/main.ts
    symbol_or_text: router
confidence: high
```

没有证据的结论不能作为硬评分项，只能作为人工审计或定性讨论。

### 7.3 共识规则

把多个参考 agent 的结果合并成 `consensus-reference.md`。

结论可信度分为：

| 可信度 | 规则 | 是否进入评分 |
| --- | --- | --- |
| `high` | 至少 2 个独立来源命中，且有源码/配置/测试证据 | 是，硬评分 |
| `medium` | 只有 1 个来源命中，但证据较强 | 是，低权重评分 |
| `low` | 主要来自推断，证据不足 | 否，只做定性分析 |
| `disputed` | 多来源冲突 | 否，进入仲裁 |

### 7.4 可运行验证

能自动验证的尽量自动验证：

- 文件是否存在。
- 符号是否存在。
- import/export 是否存在。
- package 依赖是否存在。
- 路由配置是否指向某组件。
- 测试命令是否能运行。
- 某文件修改后哪些测试或构建路径受影响。

无法自动验证的架构抽象，例如“这是分层架构”或“这个模块属于业务层”，必须要求答案给出证据链。

## 8. 实验臂定义

| 实验臂 | 允许能力 | 禁止能力 |
| --- | --- | --- |
| `Baseline` | 目录浏览、文件读取、文本搜索、项目原生 README/docs | 禁止读取任何工具产物和 reference 目录 |
| `GitNexus` | GitNexus 索引、查询、augment、MCP/CLI，源码校验 | 禁止使用其他工具产物和 reference 目录 |
| `graphify` | graphify 图谱、报告、wiki、MCP/CLI，源码校验 | 禁止使用其他工具产物和 reference 目录 |
| `Understand-Anything` | knowledge graph、layer、tour、domain graph、dashboard/chat/explain，源码校验 | 禁止使用其他工具产物和 reference 目录 |
| `codegraph` | codegraph index、context、trace、explore、impact、callers/callees，源码校验 | 禁止使用其他工具产物和 reference 目录 |

公平性要求：

- 每个实验臂使用相同任务、相同模型、相同上下文预算、相同时间上限。
- 工具组可以使用工具定位信息，但最终答案必须列出证据。
- 工具组不能因为工具输出看起来合理就跳过源码校验。
- 所有工具失败、索引失败、超时都要记录，不允许悄悄重跑到成功为止。

## 9. 执行矩阵

一个完整 run：

```text
repo_id x model_id x arm_id x task_id x round_id
```

MVP 建议：

| 维度 | 数量 |
| --- | ---: |
| 仓库 | 3 个，小中大各 1 |
| 实验臂 | 5 个 |
| 模型 | 2 个 |
| 任务 | 每仓库 6 个 |
| 轮次 | 2 轮 |
| 总运行数 | `3 x 5 x 2 x 6 x 2 = 360` |

正式评测建议：

| 维度 | 数量 |
| --- | ---: |
| 仓库 | 9 个，小中大各 3 |
| 实验臂 | 5 个 |
| 模型 | 3 个 |
| 任务 | 每仓库 8 个 |
| 轮次 | 3 轮 |
| 总运行数 | `9 x 5 x 3 x 8 x 3 = 3240` |

模型至少覆盖：

- 强推理模型。
- 中等成本模型。
- 开源或本地模型。

## 10. 标准 Prompt

### 10.1 Baseline Prompt

```text
你正在参与代码架构识别评测，当前实验臂是 Baseline。

限制：
- 只能使用普通源码阅读能力：目录浏览、文件读取、文本搜索。
- 可以读取仓库原生 README、docs、配置、测试。
- 禁止读取任何预构建图谱、索引、知识库、dashboard、reference 目录或其他工具产物。
- 不允许联网。

任务：
{{question}}

输出要求：
1. 结论摘要
2. 主要模块与职责
3. 分层关系、依赖关系或调用/数据流
4. 关键入口、关键文件、关键符号
5. 证据：每个关键结论至少给出文件路径或符号依据
6. 不确定点：说明哪些判断置信度不足
```

### 10.2 工具组 Prompt

```text
你正在参与代码架构识别评测，当前实验臂是 {{tool_name}}。

限制：
- 当前唯一允许的专门工具是 {{tool_name}}。
- 应优先使用 {{tool_name}} 的索引、图谱、查询、报告或 dashboard 产物来定位架构信息。
- 可以读取源码做必要事实校验。
- 禁止读取其他工具产物、reference 目录或其他实验臂结果。
- 不允许联网。

任务：
{{question}}

输出要求：
1. 结论摘要
2. 主要模块与职责
3. 分层关系、依赖关系或调用/数据流
4. 关键入口、关键文件、关键符号
5. 证据：区分“工具发现”和“源码验证”
6. 工具贡献：说明工具帮助发现了哪些 Baseline 可能难发现的信息
7. 不确定点：说明哪些判断置信度不足
```

### 10.3 Judge Prompt

```text
你是代码架构识别评测员。你会看到：
1. 任务问题
2. 候选答案
3. 参考答案池，包括高置信事实、中置信事实、争议项和证据

评分原则：
- 只奖励能被参考事实或源码证据支持的结论。
- 对缺少证据但合理的推断，可以给少量抽象质量分，但不能给事实分。
- 对编造的模块、调用链、依赖关系、入口点扣分。
- 对明确表达不确定性且没有误导的内容少扣分。
- 不因答案更长、更流畅而额外加分。

请输出 JSON：
{
  "module_coverage": 0-100,
  "module_precision": 0-100,
  "dependency_correctness": 0-100,
  "entrypoint_accuracy": 0-100,
  "call_chain_quality": 0-100,
  "impact_quality": 0-100,
  "abstraction_quality": 0-100,
  "evidence_quality": 0-100,
  "hallucination_penalty": 0-100,
  "overall_score": 0-100,
  "comments": "简短说明主要加分和扣分原因"
}
```

## 11. 评分体系

总分 100 分。

| 一级指标 | 权重 | 说明 |
| --- | ---: | --- |
| 架构事实覆盖 | 25 | 模块、入口、关键文件、基础设施组件是否命中 |
| 关系与路径恢复 | 20 | 依赖关系、调用链、数据流、方向是否正确 |
| 影响分析能力 | 15 | 变更影响面、直接/间接影响、漏报误报 |
| 架构抽象质量 | 15 | 是否能从文件上升到模块、分层、职责和阅读路径 |
| 证据质量 | 10 | 结论是否可追溯到文件、符号、工具输出或验证命令 |
| 成本与效率 | 10 | 索引耗时、任务耗时、token、工具调用、文件读取 |
| 稳定性与可用性 | 5 | 多轮波动、工具安装成功率、索引失败率 |

核心自动指标：

| 指标 | 计算方式 |
| --- | --- |
| 事实召回 | 答案命中的高/中置信事实数 / 参考事实数 |
| 事实精确 | 答案中被证据支持的事实数 / 答案提出的事实数 |
| 关系召回 | 命中的依赖边、调用边、入口链路数 / 参考关系数 |
| 幻觉率 | 无证据或与参考事实冲突的关键结论数 / 关键结论数 |
| 证据覆盖 | 带文件/符号/命令证据的关键结论数 / 关键结论数 |
| 稳定性 | 同条件多轮答案分数标准差 |
| 工具 ROI | 工具组相对 Baseline 的分数增益 / 归一化成本 |

## 12. 成本与效率记录

每个 run 至少记录：

```yaml
index_time_seconds: 0
task_time_seconds: 0
total_time_seconds: 0
tool_calls: 0
file_reads: 0
search_calls: 0
tokens_input: null
tokens_output: null
tokens_total: null
estimated_cost_usd: null
failure:
  occurred: false
  stage: null
  reason: null
```

工具组要区分：

- cold index 成本：第一次建索引。
- warm query 成本：索引已存在时单任务查询成本。
- maintenance 成本：增量更新、freshness check、重建失败等。

## 13. 各工具执行 SOP

### 13.1 Baseline

重点记录：

- 文件读取数。
- 搜索次数。
- 是否只停留在目录总结。
- 大仓库上是否遗漏跨模块关系。

### 13.2 GitNexus

重点记录：

- analyze/index 是否成功。
- 是否使用 augment。
- 查询次数和查询类型。
- community、flow、risk、call graph 信息是否进入答案。
- 相比 Baseline 是否减少无效搜索。

### 13.3 graphify

重点记录：

- 纳入了哪些资料：代码、README、docs、图像、PDF 等。
- 图谱节点数、边数、社区数。
- LLM 抽取成本。
- wiki/report 是否被答案引用。
- 文档语义是否提升业务解释，或是否引入噪声。

### 13.4 Understand-Anything

重点记录：

- knowledge graph、layer、tour、domain graph 是否成功生成。
- 语义分批是否触发。
- dashboard/chat/explain 中哪些信息被使用。
- onboarding、分层、领域概念任务是否明显领先。

### 13.5 codegraph

重点记录：

- index 耗时、索引大小、语言识别情况。
- context、trace、explore、impact、callers/callees 调用次数。
- 对调用链和影响分析是否减少断链。
- 大仓库是否显著减少文件读取和 token。

## 14. 多轮与统计

每个 `(repo, model, arm, task)` 至少 3 轮。MVP 可先 2 轮。

报告以下统计项：

| 统计项 | 作用 |
| --- | --- |
| mean_score | 平均质量 |
| median_score | 抵抗极端值 |
| stddev | 稳定性 |
| p10/p90 | 最差和最好表现区间 |
| win_rate_vs_baseline | 同仓库同模型同任务超过 Baseline 的比例 |
| gain_vs_baseline | 相对 Baseline 平均增益 |
| failure_rate | 安装、索引、查询、回答失败比例 |

建议排序公式：

```text
rank_score =
  0.45 * mean_quality_score
+ 0.20 * gain_vs_baseline
+ 0.15 * evidence_score
+ 0.10 * efficiency_score
+ 0.05 * stability_score
+ 0.05 * usability_score
```

## 15. 盲评和仲裁

正式评分时要隐藏实验臂名称：

1. 把答案脱敏为 `answer_001.md`。
2. 去掉工具名、运行目录、明显提示词痕迹。
3. Judge 只看任务、候选答案、参考答案池和证据。
4. 每个答案至少由两个 judge 评分。
5. 如果总分差超过 15 分，进入仲裁。

仲裁不要求人熟悉整个仓库，只要求检查争议 claim 的证据是否成立。

## 16. 最终报告结构

最终报告至少包含：

1. 实验设置：仓库、模型、工具版本、任务数、轮次。
2. 总分排名：5 个实验臂整体得分。
3. 相对 Baseline 增益：四个工具分别提升多少。
4. 按仓库规模拆分：小/中/大型仓库上的表现。
5. 按任务类型拆分：宏观架构、调用链、影响分析、onboarding。
6. 按模型拆分：强模型、中等模型、本地模型的收益差异。
7. 成本与效率：索引、查询、token、文件读取、耗时。
8. 稳定性：多轮标准差、失败率。
9. 典型案例：每个工具最好和最差的样本。
10. 选型建议：主选型、补充方案、暂不采用原因。

推荐结论模板：

```text
在本次评测的 N 个仓库、M 个模型、K 个任务、R 轮重复中：

- codegraph 在调用链和影响分析任务上平均比 Baseline +X 分，主要优势是低幻觉和高证据覆盖。
- Understand-Anything 在 onboarding 和架构解释任务上平均比 Baseline +Y 分，适合面向人的理解产品。
- graphify 在包含文档和设计资料的仓库中语义收益最大，但纯代码结构任务波动较高。
- GitNexus 在 agent 工作流效率、augment 和多轮稳定性上表现突出。
- 小型仓库中 Baseline 已经较强，工具 ROI 未必最高；中大型仓库中工具增益更明显。

推荐主选型：____
推荐补充方案：____
暂不采用或延后采用：____
```

## 17. 决策规则

不要只看总分，应按目标选择。

| 目标 | 首选指标 | 决策方式 |
| --- | --- | --- |
| 做工程底座 | 调用链、影响分析、低幻觉、稳定性 | 选这两类任务长期第一且失败率低的工具 |
| 做 onboarding 产品 | 架构抽象、领域概念、阅读路径 | 选 onboarding 增益最大的工具 |
| 做组织知识库 | 文档融合、语义解释、跨资料图谱 | 选文档语义任务收益最大且证据质量可接受的工具 |
| 降低模型成本 | 中等/本地模型增益、ROI | 选能让低成本模型接近强模型 Baseline 的工具 |
| 接入现有 agent 工作流 | 安装复杂度、查询效率、MCP/CLI 稳定性 | 选集成最顺、失败率最低的工具 |

最终输出三段式选型：

1. `主选型`：最适合作为核心技术底座的方案。
2. `补充方案`：在特定任务上明显更强、适合组合使用的方案。
3. `暂不采用原因`：当前目标下的成本、稳定性或适配问题。

## 18. 执行 agent 总提示词

下面这段可以直接给执行 agent：

```text
你要执行 AI 辅助识别代码架构工具评测。

输入：
- 源码仓库根目录：{{repos_root}}
- 可用模型列表：{{models}}
- 可用工具：Baseline、GitNexus、graphify、Understand-Anything、codegraph
- 输出目录：{{benchmark_output_dir}}

请严格按以下流程执行：
1. 扫描 repos_root 下的 git 仓库，生成 repos-manifest.yaml，并按小/中/大分层。
2. 为每个入选仓库生成 repo-profile.yaml，不使用被评测工具。
3. 基于 repo-profile 自动生成 tasks.yaml，每个仓库至少 8 个任务。
4. 构建 reference：由多个独立 agent 生成参考答案池，所有关键 claim 必须绑定源码、配置、测试或工具证据。
5. 对每个 repo/model/arm/task/round 执行实验。正式 run 禁止读取 reference 目录和其他实验臂产物。
6. 保存 prompt、answer、tool-log、command-log、metrics。
7. 用 reference 对答案打分，记录事实覆盖、关系正确性、影响分析、抽象质量、证据质量、成本、稳定性。
8. 对答案脱敏并做双 judge 评分，分歧超过 15 分时仲裁。
9. 汇总 scores.csv 和 final-report.md，报告总分、相对 Baseline 增益、按规模/任务/模型拆分、成本、失败率和选型建议。

原则：
- 不要求人提前熟悉仓库。
- 不能把无证据的 LLM 推断当真值。
- 工具失败必须记录为结果的一部分。
- 所有结论必须可追溯。
```

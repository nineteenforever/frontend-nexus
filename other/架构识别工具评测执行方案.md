# AI 辅助识别代码架构工具评测执行方案

## 0. 实验结论要回答什么

本评测的目标不是证明某个工具“看起来更酷”，而是用可复现实验回答：

1. 不使用专门工具时，agent 仅靠源码阅读能识别到什么程度。
2. 使用 `GitNexus`、`graphify`、`Understand-Anything`、`codegraph` 后，架构识别质量、效率和稳定性分别提升多少。
3. 工具收益是否随仓库规模变化：小仓库是否不明显，大仓库是否显著。
4. 工具是否能降低模型能力门槛：中等模型或开源模型使用工具后，是否接近强模型不用工具。
5. 哪个方案适合作为后续技术选型的主线，哪个更适合作为补充能力。

最终输出应是一份选型报告，包含每个方案相对 `Baseline` 的绝对得分、增益、成本、稳定性和适用场景。

## 1. 实验臂设计

共 5 个实验臂。

| 实验臂 | 是否使用专门工具 | agent 允许能力 | 禁止能力 |
| --- | --- | --- | --- |
| `Baseline` | 否 | `ls/find/rg/sed/cat`、普通文件读取、普通搜索 | 禁止使用任何预建图谱、索引、dashboard、MCP、工具生成摘要 |
| `GitNexus` | 是 | GitNexus 索引、查询、augment、MCP/CLI 产物，以及必要源码验证 | 禁止使用其他三种工具产物 |
| `graphify` | 是 | graphify 图谱、报告、wiki、MCP/CLI 查询，以及必要源码验证 | 禁止使用其他三种工具产物 |
| `Understand-Anything` | 是 | knowledge graph、layer、tour、domain graph、dashboard/chat/explain 产物，以及必要源码验证 | 禁止使用其他三种工具产物 |
| `codegraph` | 是 | codegraph index、context、trace、explore、impact、callers/callees 等查询，以及必要源码验证 | 禁止使用其他三种工具产物 |

关键控制点：工具组不是“只看工具输出”，而是“优先用工具定位和组织上下文，再用源码做事实校验”。否则容易把工具的错误原样放大。

## 2. 仓库分层与样本选择

从本地 `external-repos` 或其他已下载仓库中抽样。每个规模至少 3 个仓库，正式实验建议 9 到 12 个仓库。

| 规模 | 建议 LOC | 建议文件数 | 目标用途 |
| --- | ---: | ---: | --- |
| 小型 | 1k-10k | 20-200 | 验证工具在简单项目上是否存在额外成本，基线是否已经足够 |
| 中型 | 10k-100k | 200-2,000 | 观察工具对跨模块理解、调用链、影响分析的实际增益 |
| 大型 | 100k+ | 2,000+ | 检验上下文压缩、索引、图查询和稳定性的核心价值 |

选样原则：

- 覆盖不同语言和框架：TypeScript、Python、Go、Java、Rust 至少覆盖 3 类。
- 每个仓库固定 commit，记录 `git rev-parse HEAD`。
- 优先选有 README、测试、配置、示例、设计文档的真实仓库。
- 不要全选工具作者自己的仓库，避免工具对自身项目过拟合。
- 若工具不支持某语言，保留失败记录，不要临时换仓库掩盖问题。

建议先跑一个 MVP：

| 阶段 | 仓库 | 模型 | 任务/仓库 | 轮次 | 总运行数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| MVP | 3 个，小中大各 1 | 2 个 | 6 | 2 | `3 x 5 x 2 x 6 x 2 = 360` |
| 正式 | 9 个，小中大各 3 | 3 个 | 8 | 3 | `9 x 5 x 3 x 8 x 3 = 3240` |
| 加强 | 12 个 | 4 个 | 10 | 5 | 视预算决定 |

## 3. Ground Truth 制作

没有真值就只能做主观比较，所以每个仓库必须先建立 `ground-truth`。

### 3.1 每个仓库的真值内容

```yaml
repo_id: string
repo_name: string
commit: string
size_bucket: small | medium | large
languages:
  - string
architecture:
  summary: string
  layers:
    - name: string
      responsibility: string
      evidence:
        - file_or_symbol: string
modules:
  - name: string
    responsibility: string
    key_files:
      - string
    key_symbols:
      - string
dependencies:
  - from: string
    to: string
    relation: imports | calls | configures | persists | publishes | subscribes | owns
entrypoints:
  - name: string
    file: string
    symbol: string
call_chains:
  - id: string
    description: string
    nodes:
      - file: string
        symbol: string
business_flows:
  - id: string
    description: string
    modules:
      - string
impact_cases:
  - change: string
    expected_impacted_modules:
      - string
    expected_impacted_files:
      - string
known_uncertain_items:
  - string
```

### 3.2 真值生产流程

1. `GT-Agent-A` 独立整理第一版真值。
2. `GT-Agent-B` 独立复核并补充证据。
3. 人类或主评审合并冲突，标记高置信和低置信条目。
4. 低置信条目不进入硬性扣分，只作为定性讨论。

真值文件建议放在：

```text
benchmark/ground-truth/<repo_id>/ground-truth.yaml
benchmark/ground-truth/<repo_id>/evidence.md
```

## 4. 任务集设计

每个仓库至少 8 个任务，覆盖 4 类能力。所有实验臂必须回答完全相同的问题。

| 任务类型 | 任务数 | 评测重点 | 示例问题 |
| --- | ---: | --- | --- |
| 宏观架构识别 | 2 | 模块、分层、入口、职责 | “请说明该仓库的整体架构、主要模块和分层关系。” |
| 调用链/依赖分析 | 2 | 跨文件路径、关键节点、依赖方向 | “从入口 X 到核心处理 Y 的调用链是什么？” |
| 业务语义/onboarding | 2 | 抽象能力、阅读顺序、领域概念 | “新人应按什么顺序理解这个仓库？核心领域概念是什么？” |
| 变更影响分析 | 2 | 影响面、漏报、误报、证据 | “如果修改接口/函数/配置 X，会影响哪些模块和文件？” |

每个任务都需要写成机器可执行的 `task.yaml`：

```yaml
task_id: repoA-T01
repo_id: repoA
task_type: macro_architecture
difficulty: L1 | L2 | L3 | L4
question: >
  请说明该仓库的整体架构、主要模块、分层关系和关键入口。
required_output:
  - modules
  - layers
  - entrypoints
  - dependencies
  - uncertainty
scoring_keys:
  - module_recall
  - dependency_precision
  - abstraction_quality
ground_truth_refs:
  - architecture
  - modules
  - entrypoints
```

难度定义：

| 难度 | 定义 |
| --- | --- |
| `L1` | 局部定位，单目录或少量文件即可回答 |
| `L2` | 需要跨文件整合，涉及若干模块 |
| `L3` | 需要模块级抽象，不能只列文件 |
| `L4` | 系统级问题，需要架构判断、调用路径或影响面综合 |

## 5. 执行矩阵

一个完整 run 由下列维度组成：

```text
repo_id x model_id x arm_id x task_id x round_id
```

正式实验推荐：

- `repo_id`：9 个。
- `model_id`：3 个，分别代表强推理、中等成本、开源或本地模型。
- `arm_id`：5 个。
- `task_id`：每仓库 8 个。
- `round_id`：3 轮，大型仓库可增至 5 轮。

模型选择不要只看绝对能力，至少覆盖：

| 模型层级 | 用途 |
| --- | --- |
| 强推理模型 | 判断工具在高上限模型上是否仍有增益 |
| 中等成本模型 | 判断工具是否能用更低成本达到可用质量 |
| 开源/本地模型 | 判断工具是否降低私有化部署门槛 |

所有轮次必须记录模型具体版本和参数。若支持 `temperature`，建议设为 `0` 或低温度；若支持 `seed`，固定 seed，但仍保留多轮重复。

## 6. 标准 Prompt

### 6.1 Baseline Prompt

```text
你正在评测“AI 识别代码架构”的 Baseline 能力。

限制：
- 只能使用普通源码阅读能力：目录浏览、文件读取、文本搜索。
- 禁止使用任何预构建代码图谱、索引、知识库、dashboard、MCP、工具生成摘要。
- 不允许联网。

任务：
{{question}}

输出格式：
1. 结论摘要
2. 主要模块与职责
3. 分层关系或数据/调用流
4. 关键入口、关键文件、关键符号
5. 证据：每个重要结论至少给出文件或符号依据
6. 不确定点：说明哪些判断置信度不足
```

### 6.2 工具组 Prompt

```text
你正在评测“AI 识别代码架构”的工具增强能力。

当前唯一允许的专门工具是：{{tool_name}}。

限制：
- 应优先使用 {{tool_name}} 的索引、图谱、查询、报告或 dashboard 产物来定位架构信息。
- 可以读取源码做必要事实校验。
- 禁止使用其他实验臂的工具产物。
- 不允许联网。

任务：
{{question}}

输出格式：
1. 结论摘要
2. 主要模块与职责
3. 分层关系或数据/调用流
4. 关键入口、关键文件、关键符号
5. 证据：区分“工具发现”和“源码验证”
6. 工具贡献：说明工具帮助发现了哪些 Baseline 可能难发现的信息
7. 不确定点：说明哪些判断置信度不足
```

### 6.3 评分用 Judge Prompt

Judge 模型只看答案、任务和真值，不看实验臂名称。

```text
你是代码架构识别评测员。请基于 ground truth 对候选答案评分。

评分原则：
- 只奖励被 ground truth 或证据支持的结论。
- 对编造的模块、调用链、依赖关系扣分。
- 对明确表达不确定性但未误导的内容少扣分。
- 不因答案文字更流畅而额外加分。

请输出 JSON：
{
  "module_recall": 0-100,
  "module_precision": 0-100,
  "dependency_recall": 0-100,
  "dependency_precision": 0-100,
  "entrypoint_accuracy": 0-100,
  "call_chain_quality": 0-100,
  "impact_quality": 0-100,
  "abstraction_quality": 0-100,
  "evidence_quality": 0-100,
  "hallucination_penalty": 0-100,
  "comments": "简短说明主要扣分原因"
}
```

## 7. 指标与权重

总分 100 分。

| 一级指标 | 权重 | 说明 |
| --- | ---: | --- |
| 架构识别准确率 | 25 | 模块、分层、入口、职责是否命中 |
| 调用链/依赖恢复 | 20 | 调用路径、依赖方向、关键中间节点是否正确 |
| 变更影响分析 | 15 | 影响模块和文件的召回、精确率 |
| 架构抽象质量 | 15 | 是否能上升到架构层，而不是目录罗列 |
| 证据与可解释性 | 10 | 是否给出可核验文件、符号、工具证据 |
| 成本与效率 | 10 | 建索引耗时、任务耗时、token、工具调用数 |
| 稳定性与可用性 | 5 | 多轮波动、安装成功率、索引失败率 |

客观指标建议：

| 指标 | 计算方式 |
| --- | --- |
| 模块召回率 | 命中真值模块数 / 真值模块数 |
| 模块精确率 | 命中真值模块数 / 答案提出模块数 |
| 依赖召回率 | 命中真值依赖边数 / 真值依赖边数 |
| 依赖精确率 | 命中真值依赖边数 / 答案提出依赖边数 |
| 调用链节点命中率 | 命中关键节点数 / 真值关键节点数 |
| 影响面召回率 | 命中受影响项 / 真值受影响项 |
| 幻觉率 | 无证据或与真值冲突的关键结论数 / 关键结论总数 |

成本指标：

```text
total_cost = index_time_weight + task_time_weight + token_weight + failure_retry_weight
roi = (score_arm - score_baseline_same_repo_model_task) / normalized_cost_arm
```

如果暂时无法拿到真实 token 成本，先用下列代理指标：

- 总耗时。
- 工具调用次数。
- 文件读取次数。
- 搜索次数。
- 生成答案长度。
- 索引是否需要额外 LLM 调用。

## 8. 多轮与统计方法

每个 `(repo, model, arm, task)` 至少 3 轮。大型仓库建议 5 轮。

统计输出：

| 统计项 | 目的 |
| --- | --- |
| `mean_score` | 平均质量 |
| `median_score` | 降低极端值影响 |
| `stddev` | 稳定性 |
| `p10/p90` | 最差和最好表现区间 |
| `win_rate_vs_baseline` | 同仓库同模型同任务下，工具组超过 Baseline 的比例 |
| `gain_vs_baseline` | 同条件下的平均增益 |
| `failure_rate` | 安装、索引、查询、回答失败比例 |

排序时不要只看平均分，建议主排序：

```text
primary_rank_score =
  0.50 * mean_quality_score
+ 0.20 * gain_vs_baseline
+ 0.15 * stability_score
+ 0.10 * efficiency_score
+ 0.05 * usability_score
```

其中 `stability_score = 100 - normalized_stddev`。

## 9. 盲评流程

为了避免“看见工具名就觉得更好”，人工评分必须盲评。

1. 执行 agent 生成答案后，统一脱敏为 `answer_001.md`。
2. 去掉工具名、运行目录、明显提示词痕迹。
3. 评分 agent 或人工评审只看到：任务、答案、ground truth、评分表。
4. 每个答案至少由 2 个 judge 评分。
5. 如果两个 judge 总分差超过 15 分，进入仲裁。

Judge 组合建议：

- `Judge-Model-Strong`：强模型评分，主看事实和架构质量。
- `Judge-Model-Cheap`：低成本模型评分，用于观察评分稳定性。
- `Human-Reviewer`：抽样复核 10%-20%，尤其复核争议样本和最终排名接近的工具。

## 11. 每个实验臂的执行 SOP

### 11.1 通用 SOP

每次运行按相同顺序执行：

1. 清理上一轮实验产物，只保留仓库源码和该工具自己的索引缓存策略。
2. 记录仓库 commit、工具版本、模型版本。
3. 工具组先建索引，记录索引耗时、成功/失败、索引产物大小。
4. 给 agent 注入标准 prompt 和任务。
5. 记录所有命令、工具调用、文件读取、搜索、耗时。
6. 保存最终答案。
7. 运行自动评分。
8. 进入盲评队列。

### 11.2 Baseline SOP

- 允许 `rg`、`find`、`ls`、`sed`、`cat`、普通编辑器读取。
- 禁止读取工具组残留目录，例如 `.codegraph`、`.gitnexus`、graph exports、knowledge graph exports。
- 若仓库本身已有 README、docs、ARCHITECTURE 等文件，可以读取，因为这是源码仓库原生内容。

### 11.3 GitNexus SOP

记录：

- analyze/index 成功率。
- 是否使用 augment。
- 查询次数和查询类型。
- 工具返回的 call graph、flow、risk、community 信息是否被答案引用。

重点观察：

- 对多轮 agent 工作流是否减少无效搜索。
- 是否比 Baseline 更快定位关键模块。
- 是否会因预计算错误产生高置信幻觉。

### 11.4 graphify SOP

记录：

- 代码、文档、多模态资料分别是否纳入图谱。
- graph 节点数、边数、社区数。
- LLM 抽取成本。
- wiki/report 是否被答案引用。

重点观察：

- 文档和设计资料是否提升业务语义解释。
- 图谱是否引入噪声或过度抽象。
- 对纯代码调用链任务是否不如静态图工具。

### 11.5 Understand-Anything SOP

记录：

- knowledge graph、layer、tour、domain graph 是否成功生成。
- 语义 batching 或输出 chunking 是否触发。
- dashboard/chat/explain 中哪些结果被答案引用。

重点观察：

- onboarding、分层解释、领域概念任务是否显著领先。
- 高层解释是否可被源码证据支撑。
- 中大型仓库下语义分批是否提高稳定性。

### 11.6 codegraph SOP

记录：

- index 耗时、索引大小、语言识别情况。
- `context`、`trace`、`explore`、`impact` 等工具调用次数。
- unresolved reference、framework-aware、dynamic dispatch 相关结果是否有帮助。

重点观察：

- 调用链和影响分析是否显著提升。
- 大仓库是否减少文件读取和 token。
- 静态图查询是否能保持低幻觉率。

## 12. 评分细则

### 12.1 架构识别准确率，25 分

| 子项 | 分值 |
| --- | ---: |
| 主要模块召回 | 8 |
| 模块职责准确 | 6 |
| 分层关系正确 | 5 |
| 关键入口命中 | 4 |
| 重要基础设施组件命中 | 2 |

### 12.2 调用链/依赖恢复，20 分

| 子项 | 分值 |
| --- | ---: |
| 关键调用链节点命中 | 8 |
| 调用顺序和方向正确 | 5 |
| 跨模块依赖关系正确 | 4 |
| 能指出动态/间接调用的不确定性 | 3 |

### 12.3 变更影响分析，15 分

| 子项 | 分值 |
| --- | ---: |
| 影响模块召回 | 6 |
| 影响文件/符号召回 | 4 |
| 误报控制 | 3 |
| 能区分直接影响和间接影响 | 2 |

### 12.4 架构抽象质量，15 分

最终报告至少包含 8 张表或图：

2. `Gain vs Baseline`：每个工具相对 Baseline 的增益。
3. `By Repo Size`：小/中/大型仓库分别排名。
4. `By Task Type`：宏观架构、调用链、onboarding、影响分析分别排名。
5. `By Model`：不同模型下的工具收益。
6. `Cost vs Quality`：质量和成本散点图。
7. `Failure Rate`：安装、索引、查询失败率。
8. `Stability`：多轮标准差或箱线图。

推荐结论格式：

```text
在正式评测的 9 个仓库、3 个模型、8 类任务、3 轮重复中：
```

## 14. 风险与控制

| 风险 | 影响 | 控制方法 |
| --- | --- | --- |
| 工具组读到了其他工具产物 | 污染对比 | 每个 arm 使用隔离工作区，执行前扫描禁止目录 |
| Judge 偏爱更长答案 | 主观偏差 | 评分 prompt 强调事实命中，不奖励文风 |
| Ground truth 不完整 | 误扣正确发现 | 允许 evidence challenge，争议项人工仲裁 |
| 工具安装失败 | 结果不完整 | 失败也记录为可用性指标，不静默剔除 |
| 模型版本变化 | 不可复现 | 记录模型版本、日期、provider、参数 |
| 大仓库成本过高 | 实验跑不完 | 先 MVP，正式实验只扩大高价值组合 |
| 工具索引缓存影响公平 | 耗时不可比 | 同时报告 cold index 和 warm query 两套成本 |

## 16. 推荐决策规则

不要只按总分选型，建议按使用目标决策：

| 目标 | 首选指标 | 推荐判断方式 |
| --- | --- | --- |
| 做工程底座 | 调用链、影响分析、低幻觉、稳定性 | 选调用链和影响分析长期第一且失败率低的工具 |
| 做 onboarding 产品 | 架构抽象、领域概念、阅读路径 | 选 onboarding 任务增益最大的工具 |
| 做组织知识库 | 文档融合、语义解释、跨资料图谱 | 选文档语义任务收益最大且可解释性好的工具 |
| 降低模型成本 | 中等/开源模型增益、ROI | 选能让低成本模型接近强模型 Baseline 的工具 |
| 接入现有 agent 工作流 | 工具调用效率、集成复杂度 | 选安装和 agent 调用链最稳定的工具 |

最终建议使用“三段式结论”：

1. `主选型`：最适合作为核心技术底座的方案。
2. `补充方案`：在特定任务上明显更强、可组合使用的方案。
3. `暂不采用原因`：不是说工具不好，而是说明当前目标下的成本、稳定性或适配问题。
